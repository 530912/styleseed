## 2. 매핑 요청 (C-번호)

| # | 요청 | 이유 |
|---|---|---|
| C-6 | 신규 6색은 **지금처럼 `none / no` 유지.** 앱 값이 아닌 색에 `yes`를 쓰지 않는다 | 계약 규칙(K3) |
| C-7 | 6색마다 **"근사 후보" 칸을 Lab 메모나 별도 열에 사람이 확정해 기록:** ivory → white·beige 중 하나, burgundy → red·purple·brown, olive → green·brown, teal → blue·green, gold → yellow·beige·brown, silver → gray. 한 값만 확정한다. 계약 반영(converted)은 공동창업자 승인 뒤 한다 | 계약 0.2.0 기준선(S1)에서 6색 의류가 빠지지 않게 하려면 근사가 필요하다. 이 근사가 정해져야 Gemini 프롬프트 근사 규칙(앱 P1-1)도 같은 답을 쓸 수 있다 |
| C-8 | 근사값과 별도로 **색 성질 두 가지를 공동창업자 결정으로 기록:** ① 무채색처럼 다룰지(권장: ivory 예, silver·gold 예(금속색), burgundy·teal 아니오, olive 결정 필요) ② 금속색인지(gold·silver) | 엔진은 색 이름보다 "무채색 여부"로 점수가 크게 바뀐다(ivory+red: white로 근사 80 / 그대로 52). 근사값만으로는 이 성질을 전달할 수 없다 |
| C-9 | **gold·silver는 인계서 4장 9번 (가)안 권장.** 금속색을 독립된 주색상 값으로 인정하고, 공통 원칙에 금속색 예외를 한 줄 추가 | (나)안이면 앱에 금속성 속성이 없어서 정보가 사라진다. 또 gold → yellow 근사는 금 액세서리를 "유채색 충돌"로 감점한다. 1라운드 주얼리 상품은 지금 gray + 메모로만 표현된다 |
| C-10 | 인계서 4장 수정안 1~8, 11은 Claude A 입장에서 **이견 없음** | 앱·엔진에 영향이 없는 문장 정리다 |
| C-11 | multi(4장 10번)는 사람 확인 후 서명. 기본 안내 문장(4장 11번)의 "절반이 안 되면 여러 색"은 공통 원칙에 맞게 고칠 것 | 앱 프롬프트에 multi 기준을 넣을 때 Lab 문장을 그대로 옮길 예정이라, 두 문장이 서로 다르면 안 된다 |
| C-12 | 다음 인계 때 **주색상 20개를 기계가 읽을 수 있는 JSON**(키, 이름, 앱 매핑, 상태, 출처, 정의·기준)으로 함께 주기 | 이번에는 md 부록 A를 사람이 옮겨 시나리오를 만들었다. 분류 인계(JSON)와 같은 형식이면 검증을 자동화할 수 있다 |
