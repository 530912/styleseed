## 3. 하위 점수 계산

### 3.1 규칙 → 점수

각 하위 지표는 **중립 60점**에서 시작해, 그 코디에 적용되는 승인 규칙의 효과를 더한다.

```
효과 = 판정 점수 × 강도(1~5) × 확신도 계수 × 6
  판정 점수: 권장 +1 · 조건부 권장 +0.5 · 주의 −1 · 비권장 −2
  확신도 계수: High 1.0 · Medium 0.75 · Low 0.5
하위 점수 = clamp(60 + Σ 효과, 0, 100)
```

| 예 | 계산 |
|---|---|
| 권장·강도 4·High | +24 → 84 |
| 주의·강도 3·High | −18 → 42 |
| 권장 4 High + 주의 3 Medium | 60 + 24 − 13.5 = 70.5 |

- 숫자(중립 60, 배수 6, 판정 점수)는 **가설 파라미터**다. 평가 데이터로 조정하며(7장), 바꾸면 `engineVersion`의 minor를 올린다
- **적용 규칙이 하나도 없으면** 60점으로 두고 `coverage: none`을 기록한다. 이 비율(“근거 없는 판단 비율”)을 매번 보고해 규칙이 부족한 영역을 공동창업자에게 알려준다

### 3.2 규칙이 코디에 “적용”되는 조건

| 규칙 모양 | 적용 조건 |
|---|---|
| 쌍 규칙(조건 A + B) | 서로 다른 두 아이템 i, j가 있고 i가 A(대분류·속성·값), j가 B를 만족 |
| 단일 규칙(조건 A만) | 아이템 하나가 A를 만족 |
| 적용 TPO·무드·계절 | 코디 아이템들의 **공통** TPO·무드·계절에 포함될 때만 적용(코디 자체의 성격 기준이므로 화면에 따라 바뀌지 않음) |
| 적용 날씨 | Match Score에는 쓰지 않는다. **Weather Fit**(상황 적합도) 계산에만 쓴다 |

같은 규칙은 한 코디에서 한 번만 센다(여러 쌍이 맞아도 1회).

### 3.3 스타일별 예외

- `규칙 종류 = 예외`, `대상 기본 규칙 = FIT-002`처럼 기본 규칙에 연결한다
- 예외의 조건과 적용 상황이 모두 맞으면 **기본 규칙 대신** 예외 규칙의 효과를 쓴다(둘을 더하지 않음)
- 예: FIT-002 “오버핏 상의 + 와이드 하의 = 주의” → 예외 FIT-003 “street 무드면 조건부 권장”. street 무드 코디에서는 −18 대신 +9
- 예외는 기본 규칙이 승인된 경우에만 승인할 수 있다(검증기가 막음)

### 3.4 속성 변환 (앱 데이터 ↔ 속성 사전)

앱은 아직 실루엣·소재감·두께·명도·채도를 저장하지 않는다(감사 7.1). V0.1은 아래 변환표로 근사하고, 변환으로 판정한 규칙은 이유 문장에 표시하지 않는다(확신 부족). **변환표도 공동창업자 확정 대상이다.**

| 앱 값 | 속성 사전 값(제안) |
|---|---|
| colorTone bright | value light, saturation high |
| colorTone light | value light, saturation low |
| colorTone muted | value medium, saturation low |
| colorTone dark | value dark, saturation medium |
| colorTone vivid | value medium, saturation high |
| fit straight(하의) | fit regular + silhouette straight |
| fit wide(하의) | fit relaxed + silhouette wide |
| material silk / linen | material_feel fluid / crisp, thickness thin |
| material wool / knit | material_feel soft·fuzzy, thickness thick |
| material leather | material_feel glossy·heavy |

## 4. 사용자 취향 데이터가 없을 때 (User Preference 15)

| 상황 | Preference 계산 | 표시 |
|---|---|---|
| **취향 데이터 없음(지금 모든 사용자)** | 무드 규칙 점수 + 아이템 무드 일관성 = **“무드 일관성”** 으로 대신한다 | “취향 정보가 쌓이면 더 정확해져요” 안내, 지표 이름은 “무드” |
| 취향 입력 있음(Phase 3) | 0.6 × 취향 일치 + 0.4 × 무드 일관성 [가설] | “내 취향” |
| 저장·스킵 기록 쌓임(Phase 3 이후) | 규칙 기반 보정(PRD FR-DATA-05) | 〃 |

- 이렇게 하면 지금은 15점이 **전문가가 평가하는 ‘무드’ 점수와 직접 비교 가능**해진다(평가 시트의 무드 열)
- 현재 엔진의 “옷장 빈도 = 취향”은 쓰지 않는다(감사 F6)
- 대안 B: 취향 데이터가 없으면 Preference를 빼고 나머지 85점으로 다시 나눈다. 단순하지만 무드 판단이 점수에서 사라지므로 **A안(무드 일관성)을 권장**한다 — 공동창업자 결정 사항

## 5. 총점과 일관성

```
Match Score = round( Σ (가중치ᵢ × 하위 점수ᵢ) / 100 × 완성도 계수 )
완성도 계수 = 0.85 + 0.15 × (상의·하의·신발 3칸 중 채운 비율, 원피스는 상·하의 2칸)  [가설]
```

- 현재 엔진의 “약점 보정(0.88/0.94)”은 설명하기 어려워 V0.1에서 뺀다. 나쁜 조합은 `주의·비권장` 규칙이 직접 낮춘다
- **Weather Fit**(상황 적합도)은 0~100으로 따로 계산하고 Today에서 “날씨 반영” 표시와 함께 보인다. Today 순위는 `제외 규칙 통과 → Match Score → Weather Fit` 순서
- **제외 규칙:** `비권장 + 강도 5 + 적용 날씨`인 승인 규칙에 걸린 아이템은 그 날씨의 Today 후보에서 뺀다(감사 R4). 대신 넣을 옷이 없으면 “오늘 날씨에 맞는 ○○이 옷장에 없어요”를 보인다

## 6. 추천 근거 문장

| 규칙 | 내용 |
|---|---|
| 출처 | 적용된 승인 규칙의 `사용자 안내 문장`, 없으면 `판단 이유` |
| 고르기 | 효과가 큰 긍정 규칙 2개 + 부정 규칙이 있으면 주의 1개 |
| 아이템 이름 | 문장에 아이템을 넣을 때는 실제 코디의 아이템 이름(색 + 품목)만 사용 |
| 만들지 않는 경우 | 적용 규칙이 없으면 이유를 지어내지 않고 표시하지 않는다(내부에 `coverage: none`) |
| 변환으로 판정한 규칙 | 점수에는 반영, 문장에는 쓰지 않음(3.4) |
| 검증 | 단위 테스트: 모든 문장이 `firedRules`의 규칙에서 왔는지 |

## 7. 평가 데이터로 조정하는 방법

### 7.1 비교 지표

| 지표 | 무엇을 보나 |
|---|---|
| 평가자 간 일치도 | 두 사람 점수의 가중 kappa, 정확히 같은 비율, 1점 이내 비율, 종합 점수 순위 상관(`npm run fkd:compare`) — **엔진 평가의 상한선**. 사람끼리도 안 맞는 차원은 엔진에 많이 기대하지 않는다 |
| 엔진 vs 사람(종합) | 엔진 Match Score와 두 사람 종합 평균의 순위 상관(Spearman), 판정 일치(엔진 점수 ≥ 70 적합 · 50~69 조건부 · < 50 부적합 [가설]) |
| 엔진 vs 사람(차원별) | 하위 점수 ↔ 같은 차원 사람 점수(1~5 → 0~100: (점수−1)×25)의 순위 상관·평균 차이 |
| 쌍 비교 정확도 | 사람이 더 높게 본 코디를 엔진도 더 높게 본 비율 |
| 규칙 커버리지 | 하위 점수가 `coverage: none`인 비율 |

### 7.2 조정 단계

| 단계 | 데이터 | 하는 일 | 하지 않는 일 |
|---|---|---|---|
| Pilot | 코디 20개 × 2명 | 일치도 확인, 평가 기준 문장 다듬기, 불일치에서 규칙 만들기, 엔진과 큰 차이 나는 코디 원인 분석 | **가중치 숫자 조정 안 함**(표본이 너무 작음) |
| 확장 | 코디 60개 이상 | 사람의 차원 점수로 사람의 종합 점수를 가장 잘 설명하는 가중치 추정(음수 없음, 합 100, 5점 단위, 교차 검증). 엔진 파라미터(중립·배수) 조정 | 개발용으로 맞춘 숫자를 보류용 세트에서 확인하지 않고 채택하지 않음 |
| 채택 | — | 보류용 세트에서 기존보다 나아졌을 때만, **공동창업자 2명 승인** 후 새 `weightsVersion` | 사람 승인 없는 자동 반영 |

- 종합 점수를 각 차원의 평균으로 자동 계산하지 않고 **사람이 직접 매기게 한 이유**: “전문가가 각 차원을 실제로 얼마나 중요하게 보는지”를 데이터로 알아내기 위해서다
- 평가 세트는 개발용 70% / 보류용 30%로 나누고, 보류용은 조정에 쓰지 않는다

## 8. 버전 관리

| 버전 | 형식 | 언제 올리나 |
|---|---|---|
| `engineVersion` | `match-주.부.수` | 주: 계산식 구조 변경 / 부: 파라미터(중립·배수·완성도·판정 점수) 변경 / 수: 버그 수정 |
| `weightsVersion` | `w-0.1-hypothesis` → `w-0.2-pilot` … | 가중치 변경(공동창업자 승인) |
| `datasetVersion` | `fkd-<입력 해시 12자리>` | 속성 사전·규칙 CSV가 바뀌면 자동으로 바뀜 |

- 세 버전은 모든 점수 결과·평가 보고서·(Phase 1B-4 이후) 행동 기록에 함께 남긴다
- 버전마다 스냅샷 테스트 기준을 남기고, 바뀐 점을 `docs/recommendation/CHANGELOG.md`에 적는다
- 이전 버전으로 되돌릴 수 있게 가중치·ruleset 파일은 버전별로 보관한다

## 9. 앱 적용 조건 (Go 조건)

새 엔진은 아래가 **모두** 충족될 때 PO 승인을 받아 앱에 연결한다.

1. 승인 규칙이 5개 차원 각각 최소 5개 이상(총 25개 이상) [제안]
2. Pilot 20개 평가 완료 + 불일치 검토 완료
3. 엔진 Match Score와 사람 종합 평균의 순위 상관이 **현재 엔진보다 높음**(같은 20개로 비교)
4. 날씨 제외 규칙 위반 0건, 같은 코디 화면 간 점수 차이 0
5. 단위 테스트·기존 회귀 테스트 통과

그 전에는 `scripts/`에서 비교 보고서만 만든다. 앱 코드(`src/app/*`)는 바꾸지 않는다.
