# STYLESEED 패션 지식 데이터 입력 안내 (공동창업자용)

이 안내서는 개발을 몰라도 따라 할 수 있게 썼습니다. 코드를 볼 필요가 없습니다.
**패션 판단(속성 기준·스타일링 규칙·코디 평가)은 두 분이 정하고**, Claude는 그 데이터를 검사하고 추천 엔진에 연결합니다.

- 평가자 이름 대신 **ID**를 씁니다: 누나 = **E1**, 공동창업자 = **E2** (바꾸고 싶으면 처음에 정하고 끝까지 같은 ID 사용)
- 날짜는 항상 `2026-10-21`처럼 적습니다
- 여러 값을 한 칸에 넣을 때는 세로 막대 `|`로 나눕니다. 예: `office|date`

---

## 한눈에 보는 순서

| 단계 | 누가 | 무엇을 | 파일 | 예상 시간 |
|---|---|---|---|---|
| 1 | 각자 | 구글 시트 만들기 | 4개 파일 가져오기 | 15분 |
| 2 | **각자 따로** | Pilot 코디 20개 독립 평가 | `outfit_evaluation` | 60~90분 |
| 3 | 누나 | 두 평가 파일을 CSV로 내보내 Claude에게 전달 | — | 5분 |
| 4 | 함께 | 점수가 크게 다른 코디 검토·합의 | `disagreement_review` | 30~60분 |
| 5 | 함께 | 속성 사전 확정 | `garment_schema` | 60분 |
| 6 | 한 명이 작성 | 스타일링 규칙 작성 | `styling_rules` | 규칙당 3~5분 |
| 7 | **다른 한 명이** | 규칙 검토·승인 | `styling_rules` | 규칙당 1~2분 |
| 8 | 누나 | CSV로 내보내 Claude에게 전달 → 오류 목록 받으면 고치기 | — | 10분 |
| 9 | 각자 따로 | 평가 코디 60개 이상으로 확장(2~4단계 반복) | `outfit_evaluation` | — |

**왜 평가(2단계)를 규칙(6단계)보다 먼저 하나요?** 규칙을 함께 정한 뒤에 평가하면 두 분의 판단이 서로 닮아져서, “전문가 두 명이 원래 얼마나 비슷하게 보는지”를 잴 수 없습니다. 첫 20개는 아무 의논 없이 각자 평가해 주세요.

## 1단계 — 구글 시트 만들기 (각자, 15분)

프로젝트 폴더 `data/fkd/templates/`에 파일 4개가 있습니다. 누나가 두 분에게 파일을 전달해 주세요.

| 파일 | 내용 | 누가 쓰나 |
|---|---|---|
| `garment_schema.csv` | 속성 사전(카테고리·색·핏·실루엣·소재·TPO·계절·무드의 허용값) | 함께 |
| `styling_rules.csv` | 스타일링 규칙(조건 → 판정 → 이유 → 예외) | 작성자 + 검토자 |
| `outfit_evaluation.csv` | 코디 평가표(Pilot 20개가 미리 들어 있음) | **각자 따로** |
| `disagreement_review.csv` | 불일치 검토표(3단계에서 Claude가 만들어 줌) | 함께 |

가져오는 방법:
1. Google Drive → **새로 만들기 → Google 스프레드시트**
2. **파일 → 가져오기 → 업로드** → CSV 파일 선택
3. “가져오기 위치”는 **새 스프레드시트 만들기**, “구분자 유형”은 **자동 감지**
4. 첫 줄(제목 줄)은 고정해 두면 편합니다: **보기 → 고정 → 1행**

> 제목 줄(1행)의 글자, 특히 대괄호 안의 영어 `[rule_id]` 같은 부분은 **절대 바꾸거나 지우지 마세요.** Claude가 이 이름으로 열을 찾습니다. 열 순서를 바꾸는 것은 괜찮습니다.

| 파일 | 열 | 드롭다운 값 |

| outfit_evaluation | 추천해도 되나 | 예, 아니오, 모름 |
| styling_rules | 적용 날씨 | cold, cool, mild, warm, hot, rain, snow |

## 2단계 — Pilot 코디 20개 독립 평가 (각자 따로, 60~90분)

### 독립 평가 규칙 (가장 중요)

1. **각자 자기 사본을 만듭니다:** `outfit_evaluation` 시트에서 **파일 → 사본 만들기** → 이름을 `평가_E1`(누나) / `평가_E2`(공동창업자)로
2. **자기 사본은 상대에게 공유하지 않습니다.** 두 사람이 모두 끝낼 때까지 서로의 점수를 보지 않습니다
3. 평가하는 동안 **코디에 대해 의논하지 않습니다.** 궁금한 점은 `메모` 칸에 적어 두고 4단계에서 이야기합니다
4. 앱이나 Claude가 계산한 **추천 점수를 보지 않습니다**(점수에 끌려가지 않도록)
5. 한 파일에는 한 사람의 평가만 들어갑니다(두 사람이 한 시트에 같이 적으면 검증에서 오류가 납니다)

### 한 줄(코디 하나) 채우는 법

미리 채워진 칸: 코디 ID(P01~P20), 평가 상황(예: “가을 · 출근”), 아이템 1~4(예: “화이트 오버핏 면 셔츠 (#1)”). **이 칸은 고치지 마세요.**

| 칸 | 쓰는 법 | 예 |
|---|---|---|
| 평가자 ID | 내 ID | E1 |
| 색 1~5 | 색 조화·명도 대비·채도 균형·면적 비율 | 4 |
| 핏·실루엣 1~5 | 상하 볼륨·허리선·길이·레이어링 | 3 |
| 소재·계절 1~5 | 광택·두께·드레이프·텍스처, 계절과 날씨 | 4 |
| TPO 1~5 | **평가 상황**에 맞는 격식·활동성·노출 | 2 |
| 무드 1~5 | 아이템들이 같은 스타일 방향인지 | 4 |
| **종합 1~5** | 위 점수를 평균 내지 말고, **이 코디를 전체로 보고 직접 판단** | 3 |
| 판정 | 적합 / 조건부 / 부적합 | 조건부 |
| 추천해도 되나 | 이 상황의 사용자에게 앱이 이 코디를 보여줘도 되나 | 아니오 |
| 핵심 이유 | **관찰 가능한 이유**로 한두 문장 | 출근 상황인데 민소매 탑은 노출이 많아 격식이 부족함 |
| 바꾸면 좋을 아이템 | 하나만 바꾼다면 무엇을 무엇으로 | 민소매 탑 → 흰 셔츠 |
| 확신도 | 판단이 애매하면 Low | Medium |
| 평가일 | 오늘 날짜 | 2026-10-21 |
| 데이터 출처 | 그대로 `사람` | 사람 |

### 1~5점 기준 (Numbers 04_평가기준과 같음)

| 점수 | 색 | 핏·실루엣 | 소재·계절 | TPO | 무드 |
|---|---|---|---|---|---|
| 1 | 충돌이 커서 조합을 방해 | 비율·볼륨이 크게 무너짐 | 계절·물성 충돌이 심함 | 상황에 명백히 부적합 | 의도한 무드가 깨짐 |
| 2 | 불안정한 조합 | 어색함이 뚜렷 | 부조화가 눈에 띔 | 다소 부적합 | 무드 충돌 |
| 3 | 무난·중립 | 무난·조건부 | 무난 | 상황에 따라 가능 | 혼합되나 성립 |
| 4 | 대체로 조화 | 균형이 좋음 | 재질 대비·통일감이 좋음 | 대체로 적합 | 대체로 일관 |
| 5 | 의도와 대비가 명확하고 매우 조화 | 실루엣 의도가 명확하고 비율이 매우 좋음 | 소재 조합이 완성도를 높임 | 상황과 기능에 매우 적합 | 무드가 명확하고 아이템이 같은 방향을 강화 |

### 좋은 이유 vs 아쉬운 이유

| 아쉬움 | 좋음 |
|---|---|
| 이상함 | 상·하의 볼륨이 모두 커서 허리선이 사라짐 |
| 색이 별로 | 핑크와 블루가 둘 다 채도가 높아 시선이 나뉨 |
| 계절이 안 맞음 | 울 니트에 리넨 반바지라 두께감이 계절상 충돌함 |

> 사진이 없어 판단이 어려우면 `확신도 Low` + 메모에 “사진 필요”라고 적어 주세요. 다음 평가 세트부터는 이미지 링크를 넣겠습니다.

## 3단계 — 내보내서 Claude에게 전달 (누나, 5분)

1. 두 분 모두 20개를 다 채웠는지 확인
2. 각자 시트에서 **파일 → 다운로드 → 쉼표로 구분된 값(.csv)**

4. 프로젝트 폴더 `data/fkd/sheets/evaluations/`에 넣고 Claude에게 “Pilot 평가 비교해줘”라고 요청

Claude가 돌려주는 것:
- 두 분의 **일치도**(차원별로 얼마나 비슷하게 봤는지)
- `disagreement_review.csv`: **점수가 2점 이상 차이 나거나 판정이 다른 코디** 목록

## 4단계 — 불일치 검토 (함께, 30~60분)

`disagreement_review.csv`를 1단계처럼 구글 시트로 가져와 **함께** 봅니다. 이제는 서로의 점수와 이유를 봐도 됩니다.

| 칸 | 쓰는 법 |
|---|---|
| 원인 분류 | 기준 해석 차이 / 정보 부족(사진·설명) / 취향 차이 / 입력 실수 / 규칙 필요 |
| 합의 점수 · 합의 판정 · 합의 이유 | 이야기한 뒤 둘이 동의한 결과 |
| 후속 조치 | 규칙 추가 / 규칙 수정 / 평가 기준 문장 수정 / 예외 추가 / 조치 없음 |
| 관련 규칙 ID | 규칙을 만들었으면 그 ID(예: TPO-001) |
| 검토 상태 | 미검토 → 논의중 → 합의 (결론이 안 나면 보류) |

> **원래 평가 파일의 점수는 고치지 마세요.** 처음 점수는 “독립 평가 기록”으로 남기고, 합의 결과는 이 검토표에만 적습니다.

여기서 “규칙 추가”로 표시한 것이 6단계 규칙 작성의 출발점이 됩니다.

## 5단계 — 속성 사전 확정 (함께, 60분)

`garment_schema`에는 지금 **127개 값이 모두 `제안` 상태**로 들어 있습니다. 두 분이 Numbers에 정리하신 속성 사전(12개 속성)과 지금 앱이 쓰는 값을 합친 것입니다.

| 칸 | 의미 |
|---|---|
| 속성 키 · 값 키 | 영어 이름(규칙에서 이 이름을 씀). **확정 후에는 바꾸지 않기** |
| 현재 앱 값 · 앱 지원 | `예` = 앱이 이미 저장함 / `변환` = 다른 값에서 바꿔서 판단 / `아니오` = 아직 앱이 모름(규칙은 쓸 수 있지만 적용은 나중) |
| 상태 | 제안 → 검토중 → **확정** 또는 폐기 |
| 결정자 · 결정일 | 확정할 때 꼭 채움(예: `E1|E2`, `2026-10-22`) |
| 데이터 출처 | `Claude 초안` 값(예: multi, 핏의 straight·wide, 섬유 소재 목록, vintage)을 확정하려면 **출처를 `사람`으로 바꾼 뒤** 확정 |

두 분이 꼭 결정해 주실 것(메모 칸에 표시해 두었습니다):
1. **핏과 실루엣:** 앱의 핏 `straight`·`wide`를 실루엣으로 옮길지
2. **명도·채도:** 앱의 `colorTone` 5단계를 명도·채도 2축으로 바꾸는 변환표(`MATCH_SCORE_V0.1.md` 3.4)가 맞는지
3. **TPO:** `school`, `active`를 추가할지
4. **무드:** `romantic`, `edgy`, `vintage`를 쓸지
5. **소재:** 섬유(면·울 …)와 소재감(빳빳함·광택 …)을 둘 다 쓸지

> 규칙은 **확정된 값만** 쓸 수 있습니다. 확정 안 된 값을 쓴 규칙은 승인해도 검증에서 오류가 납니다.

## 6단계 — 스타일링 규칙 작성 (한 명이 작성)

`styling_rules`의 `EX-`로 시작하는 8줄은 **예시**입니다. 7줄은 Numbers의 룰북·예외사례 시트에 있던 예시를 옮긴 것이고, EX-MAT-002(혹한기 실크·리넨)는 Claude가 만든 예시입니다. 예시는 추천에 절대 쓰이지 않습니다. 동의하는 예시가 있으면 **새 줄에 새 ID로 옮겨 적고** 출처를 `사람`으로 바꿔 주세요.

| 칸 | 쓰는 법 | 예 |
|---|---|---|
| 규칙 ID | 차원 약자 + 세 자리 번호. 색 `COL-`, 핏·실루엣 `FIT-`, 소재·계절 `MAT-`, TPO `TPO-`, 무드 `MOOD-` | FIT-001 |
| 버전 | 처음은 1. 승인된 규칙을 고칠 때는 **줄을 새로 추가**하고 버전을 2로 | 1 |
| 규칙 종류 · 대상 기본 규칙 | 보통 `기본`. 기본 규칙을 깨도 되는 경우는 `예외` + 대상 규칙 ID | 예외, FIT-001 |
| 평가 차원 | 색 / 핏·실루엣 / 소재·계절 / TPO / 무드 | 핏·실루엣 |
| 조건 A 대분류 · 속성 · 값 | 대분류는 top·bottom 등 또는 `any`(아무 아이템). 속성·값은 **속성 사전의 영어 키** | top · fit · oversized |
| 조건 B | 두 아이템의 조합일 때. 아이템 하나에 대한 규칙이면 비워 둠 | bottom · silhouette · wide |
| 적용 TPO·무드·계절 | 이 상황에서만 성립하면 적음(아니면 비움) | street |
| 적용 날씨 | 날씨 규칙일 때만 | cold\|snow |
| 판정 · 강도 | 권장/조건부 권장/주의/비권장, 얼마나 강한지 1~5 | 주의 · 3 |
| 판단 이유 | **관찰 가능한 이유**(10자 이상) | 상·하의 볼륨이 동시에 커져 허리선이 흐려짐 |
| 사용자 안내 문장 | 앱에 보일 문장(친근하게, 40자 안팎). 비우면 판단 이유를 씀 | 상의와 하의가 모두 넉넉해 허리선이 흐려질 수 있어요 |
| 예외·주의 사항 | 이 규칙이 안 맞는 경우 | 허리선을 드러내면 괜찮음 |
| 확신도 | 애매하면 Low | High |
| 작성자 | 내 ID | E1 |
| 승인 상태 | 처음엔 `초안`, 다 쓰면 `검토중` | 검토중 |
| 데이터 출처 | `사람` | 사람 |

규칙을 쓸 때 기억할 것(Numbers 작업지시서 원칙과 같습니다):
- 한 규칙은 한 차원만 판단합니다
- “좋다/나쁘다”가 아니라 **왜** 그런지 씁니다
- 트렌드나 무드 때문에 달라지면 **기본 규칙 + 예외 규칙**으로 나눕니다
- 확실하지 않으면 확신도를 낮추고 예외 조건을 적습니다

---

## 7단계 — 규칙 승인 (다른 한 명이)

규칙은 **작성자가 아닌 다른 사람**이 승인해야 추천에 쓰입니다.

1. `검토중` 규칙을 읽고, 동의하면 `검토자`에 내 ID, `승인 상태`를 **승인**, `승인일`에 오늘 날짜
2. 동의하지 않으면 `보류` + 메모에 이유 → 작성자와 이야기
3. 더 이상 쓰지 않을 규칙은 `폐기`(지우지 말고 남겨 두기)

**추천에 실제로 쓰이는 규칙의 조건 (하나라도 빠지면 쓰이지 않음)**

| 조건 | |
|---|---|
| 승인 상태 = 승인 | ✔ |
| 데이터 출처 = 사람 | ✔ |
| 작성자 ≠ 검토자 | ✔ |
| 승인일 있음 | ✔ |
| 사용한 속성값이 모두 속성 사전에서 확정 | ✔ |
| 예외 규칙이면 대상 기본 규칙도 승인 | ✔ |

## 8단계 — 내보내서 검사받기 (누나, 10분)

1. 세 시트를 각각 **파일 → 다운로드 → .csv**
2. 이름을 정확히: `garment_schema.csv`, `styling_rules.csv`, `disagreement_review.csv`
3. 프로젝트 폴더 `data/fkd/sheets/`에 넣고 Claude에게 “데이터셋 검사해줘”라고 요청

Claude는 `npm run fkd:validate`로 검사해 **오류 목록(몇 행에 무슨 문제)** 을 한국어로 알려드립니다. 예:

```
오류 styling_rules.csv 14행: 작성자와 검토자는 서로 다른 사람이어야 해요
오류 styling_rules.csv 21행: 승인 규칙은 '확정'된 속성값만 쓸 수 있어요: silhouette:volume
```

시트에서 고친 뒤 다시 내보내면 됩니다. 오류가 0개가 되면 Claude가 **승인된 규칙만** 모아 엔진용 파일을 만듭니다(`npm run fkd:build`).

## 9단계 — 평가 세트 확장 (60개 이상)

- Pilot이 끝나면 Claude가 새 코디 40개 이상을 평가표에 추가합니다(실제 옷 사진 링크 포함 예정)
- 2~4단계를 같은 방식으로 반복합니다(각자 사본, 독립 평가, 불일치 검토)
- 60개가 모이면 두 분의 평가로 Match Score 가중치(색 25 · 핏/실루엣 25 · TPO 20 · 소재/계절 15 · 취향 15)를 점검합니다. 가중치를 바꿀 때는 **두 분의 승인**을 받습니다

## 자주 묻는 것

| 질문 | 답 |
|---|---|
| 예시 줄을 지워도 되나요? | 지워도 되고 남겨도 됩니다. 예시는 검사·집계에서 자동으로 빠집니다 |
| 승인한 규칙을 고치고 싶어요 | 그 줄을 고치지 말고, 같은 ID로 새 줄을 만들어 버전을 2로 올린 뒤 다시 승인합니다. 이전 기록이 남아야 점수 변화를 설명할 수 있습니다 |
| 둘 다 확신이 없어요 | 확신도 Low로 적고 승인은 보류해 두세요. 평가 데이터가 쌓이면 다시 봅니다 |
| 사진이 없으면 판단이 어려워요 | 메모에 “사진 필요”. 다음 평가 세트부터 이미지 링크를 넣습니다 |
| Claude가 만든 값이나 규칙은 바로 쓰이나요? | 아니요. `Claude 초안`은 두 분이 확인하고 출처를 `사람`으로 바꿔 승인하기 전에는 절대 쓰이지 않습니다 |
| Numbers 파일은 어떻게 하나요? | 그대로 보관합니다. 속성 사전·평가 기준·예시 규칙은 이미 이 템플릿에 옮겨 두었습니다 |
