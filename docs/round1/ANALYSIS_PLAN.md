## 1. 공통 규칙

| 항목 | 규칙 |
|---|---|
| 분석 대상 | `test_env = research`, 참가 코드 `R1-P01~R1-P21` 중 `experiment_assigned`가 있는 사람 |
| 제외 | 리허설 코드 `R1-T*`, `qa`·`dev`·`rehearsal` 환경, 형식 오류 이벤트, 같은 `event_id` 재전송, 1회 이벤트의 두 번째 이후, 고려·거절 중 두 번째 선택, Paywall 노출 전 선택. **제외 건수는 이유별로 보고서에 적는다**(`r1_plus_exclusions.json`) |
| 참가자 제외 | 연구 동의 철회자(데이터 삭제 후 "철회 n명"만 기록), 대상 조건(20~34세 여성) 불충족이 사후 확인된 사람. 그 밖의 이유로 참가자를 빼지 않는다 |
| 비율 표기 | 항상 **"분자/분모"** 를 함께 적는다(예: 3/6). 소수점 비율만 쓰지 않는다 |
| 검정 | 그룹당 6명이라 유의성 검정으로 결론을 내리지 않는다. 필요하면 참고로 정확 검정 p값과 비율 구간을 붙이되 "참고"라고 쓴다 |
| 결과 표현 | 쓸 수 있는 말: "탐색적으로 ~경향이 보였다", "6명 중 n명", "인터뷰에서 반복된 이유는". 쓰면 안 되는 말: "최적 가격은 ~원으로 확인", "전환율 n%", "통계적으로 유의", "검증 완료", "매출 발생"(실제 정산 없이) |
| 기준 변경 | 결과를 본 뒤 신호 기준(5장)을 바꾸지 않는다. 바꿔야 하면 원래 기준의 결과와 바꾼 기준의 결과를 둘 다 적는다 |
| 행동 단계 | L1 노출 · L2 클릭 · L3 공식몰 이동 · L4 구독 고려 · L5 실제 구매(브랜드 보고) · L6 실제 매출(정산). 아래 단계 값을 위 단계 성과로 쓰지 않는다(BM 계획 2장) |

## 3. 데이터 처리 순서 (가격·커머스 이벤트)

1. 원자료 받기(방식: QA 검증 후 운영 테이블 승인 시 DB, 아니면 기기 내보내기 파일)
2. `node scripts/round1/events.mjs <파일> --out <폴더>` — 중복 ID 제거 → 형식 검사 → 환경·리허설 제외 → 1회·선택 규칙 → 참가자 표 → 그룹 표
3. 관찰 기록지·설문을 참가 코드로 연결(PO 보관 파일, Git 밖)
4. 보고서 작성(6장)

## 4. 해석 방식

| 결과 모양 | 해석 문장 예 | 다음 행동 |
|---|---|---|
| 한 가격 그룹의 고려가 다른 그룹보다 2명 이상 많음 | "탐색적으로 월 ○원에서 고려가 많았다(6명 중 n명). 표본이 작아 가격 효과로 단정할 수 없다" | 2라운드에 그 가격 부근을 더 큰 표본으로 재실험 |
| 세 그룹 차이가 1명 이하 | "이번 표본에서는 가격에 따른 뚜렷한 차이가 보이지 않았다" | 가격보다 기능 가치·이유를 인터뷰에서 정리 |
| 모든 그룹에서 고려 1명 이하 | "세 가격 모두에서 구독 고려가 낮았다" | 기능 구성 재설계(인터뷰 이유 기반) |
| 고려는 높은데 인터뷰에서 "실제로는 안 낼 것" | 의향과 실제 결제 의사의 차이로 보고 | 인터뷰 응답을 의향보다 우선 근거로 |
| 공식몰 이동은 있으나 브랜드 회신 없음 | "공식몰 이동 n명. 실제 구매는 측정하지 못했다" | 2라운드 파트너 계약에 주문 확인 조항 |

## 5. 탐색적 신호 기준 (실험 전 확정 — PO 확인 필요)

`BM_VALIDATION_PLAN.md` 4장의 제안값을 그대로 적는다. 첫 세션 전에 PO가 확정하면 이 표를 동결한다.

| 지표 | "더 볼 가치 있음" | "재설계" |
|---|---|---|
| PLUS 유용성(Q-P1 4·5점) | 응답자 과반 | 3점 이하가 과반 |
| 가격별 구독 고려 | 한 그룹에서 노출 6명 중 3명 이상 | 세 그룹 모두 1명 이하 |
| 공식몰 이동 | 상품을 본 참가자의 1/3 이상 | 0~1명 |
| 단위경제성 | 사용자당 월 변동비 ≤ 2,900원의 10% | ≥ 30% |

이 기준은 **팀 내부 판단용**이다. 공식 평가 기준이나 통계적 통과 기준이 아니다.
