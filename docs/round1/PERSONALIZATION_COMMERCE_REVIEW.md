# 코어·취향 기반 추천 ↔ 상품 추천 연결 구조 검토

- 작성: 2026-10-19 (Claude A, R1-01) · 상태: **검토안 — 코드 변경 없음**
- 요청: "코어·취향 기반 추천과 상품 추천의 연결 구조는 기존 개인화 기능을 우선 활용해 검토"
- 결론 요약: 새 개인화 엔진을 만들지 않는다. **기존 3개 경로(Missing Item, 옷장 취향 점수, Core 교체 추천)를 실제 상품 카탈로그 하나에 연결**하고, 주얼리는 새 "포인트 아이템" 경로가 필요하다. Core 경로는 데모 규칙(Claude 작성, 공동창업자 미승인)을 쓰므로 1라운드에는 **콘셉트 시연으로만** 쓴다

| 경로 | 재사용 | 새로 만들 것 | 1라운드 사용 | 품질 관문 |
|---|---|---|---|---|
| **A. Missing Item → 상품** | Missing 제안, Shop 매칭 점수, 화면 | 카탈로그 연결(Mock 대신), 동점 정렬에 옷장 취향, 공식몰 버튼·이벤트 | **기본 경로** | E1·E2가 "이 옷장에 맞는 상품인가" 1~5점 검수, 평균 3 이상(BM 계획 5장) |
| **B. 포인트 아이템 → 액세서리(주얼리)** | `getCompatibilityScore`(액세서리 조합 지원) | 코디 결과 아래 "포인트 아이템" 목록(최대 3개), 이벤트 | **주얼리 허가가 있을 때만** | 경로 A와 같은 검수. 주얼리는 현재 속성 체계가 거칠어(소재 `other`, 색 `gray`로 실버 표현) 검수에서 부적합이 많으면 노출하지 않음 |
| **C. Core → 상품** | Core 데모 흐름 전체, `getCoreUpgradeSuggestions` | 후보를 Mock 대신 카탈로그로(`Product` 형태 변환) | **콘셉트 시연만**(실험 이벤트 `source=core`는 기록하되 커머스 PoC 결과와 분리 보고) | POETCORE 데모 규칙을 E1·E2가 검토·승인하기 전에는 "검증된 추천"으로 쓰지 않음 |

### 2.1 PLUS와 상품 추천의 경계

- PLUS(구매 전 옷장 활용도 분석)는 사용자가 **스스로 고른** 구매 예정 옷을 분석한다. 상품 추천(경로 A~C)과 섞지 않는다.
- 상품 상세에 "내 옷장과 N벌 어울림"을 보여주면 PLUS의 가치를 Paywall 전에 공짜로 보여주는 셈이 되어 가격 실험 조건이 흐려진다. **1라운드에서는 상품 상세에 활용도 수치를 넣지 않는다.** 2라운드에 PLUS 기능 안에서 연결을 검토한다.

### 2.2 기존 개인화의 한계와 1라운드 처리

| 한계 | 처리 |
|---|---|
| 명시적 취향 입력·피드백이 없다(FR-DATA-04·05 Planned) | 만들지 않는다. 사후 인터뷰에서 "추천 상품이 내 취향과 맞았는지"를 묻는다 |
| Missing 제안 규칙과 Core 규칙이 패션 전문가 검증 전이다 | 실험에 실제로 노출되는 상품 목록을 E1·E2가 미리 검수하고, 부적합 상품은 카탈로그에서 뺀다 |
| 화면 간 점수 불일치(Looks 77 / Today 83) | 실험 화면은 엔진 B(MATCH) 하나만 표시 |
| 상품 속성이 앱 속성과 달라 매칭이 안 될 수 있다 | 상품 CSV를 앱 속성 목록과 같은 값만 받게 함(계약 `product-catalog-v0.1.json`, 테스트로 동기화 확인) |

## 3. 2라운드로 넘길 것

- 명시적 취향 입력 + 피드백 기반 가중치(FR-DATA-04·05)
- Core 규칙을 Fashion Knowledge Dataset 승인 규칙으로 교체(Phase 3 FR-CORE)
- 승인 규칙 기반 새 Match Score로 상품 순위 계산
- 상품 상세 안의 PLUS 활용도 연결
- 상품 DB 테이블·Feed/API(지금은 앱 내장 파일)
