# PLUS 가격 실험 프로토콜 — 구매 전 옷장 활용도 분석

- 작성: 2026-10-19 (Claude A) · 상태: **제안 — PO 승인 전. 코드 변경 없음**
- 상위 계획: `BM_VALIDATION_PLAN.md`(G3·G4), `SPRINT_ROADMAP.md`(R1-02-02~09)
- 실험 ID: `r1-plus-price-v1`

---

## 1. 목적과 해석 한계

| 항목 | 내용 |
|---|---|
| 질문 | 대표 유료 기능 **"구매 전 옷장 활용도 분석"** 을 써 본 타깃 사용자가 월 2,900원 / 4,900원 / 6,900원 중 배정된 가격에서 구독을 **고려**하는가 |
| 기능 정의 | 사려는 옷(실제 구매 예정 의류)의 사진을 분석해, 사용자의 기존 옷장과 몇 벌·몇 개 코디로 어울리는지, 비슷한 옷을 이미 갖고 있는지를 보여준다 |
| 측정하는 것 | 가격별 **구독 고려 의향**(행동이 아님), 거절, 선택까지 걸린 시간, 완료·이탈, 인터뷰 응답 |
| 측정하지 않는 것 | 실제 결제, 구독 전환율, 매출. 이 실험에서는 어떤 결제도 일어나지 않는다 |
| 해석 한계 | 그룹당 6명의 **탐색적 실험**이다. 그룹 간 차이가 1~2명이면 우연으로도 생긴다. **최적 가격을 확정했다고 보고하지 않는다.** 의향은 실제 결제보다 높게 나오는 경향이 있다(PRD FR-SUB-08) |
| 참고 | 사업계획서 가격 가설(월 5,900원 / 연 59,000원)은 이 실험의 세 가격 사이에 있다. 연간 가격은 보여주지 않는다(가격 1개만 노출 조건) |

## 2. 참가자와 그룹 배정

| 항목 | 내용 |
|---|---|
| 대상 | 20~34세 여성, 온라인 패션 구매 경험, **실제로 사려고 고민 중인 옷이 1벌 이상** 있는 사람 |
| 목표 인원 | 18명(A·B·C 각 6명). 예비 3명 |
| 그룹·가격 | A = 월 2,900원 · B = 월 4,900원 · C = 월 6,900원 |
| 참가 코드 | `R1-P01` ~ `R1-P21`(본 실험), `R1-T01` ~ `R1-T03`(리허설, 분석에서 제외). 코드에는 개인정보가 없다 |
| 배정 방식 | **블록 무작위 배정**: 3개씩 묶은 블록 7개 안에서 A·B·C 순서를 무작위로 섞은 표를 R1-02에서 고정 시드로 한 번 만들고, 표의 해시를 이 문서에 기록한 뒤 바꾸지 않는다. 참가자는 등록 순서대로 다음 코드를 받는다 → 18명이 오면 6·6·6 |
| 고정 | 그룹은 **코드로만 결정**된다(앱에 내장한 고정 표). 앱 재설치·다른 기기·다시 로그인해도 같은 코드는 같은 그룹이다. 한 코드는 한 계정에서만 쓴다(9장 AC-2) |
| 이탈 처리 | 배정 후 이탈해도 그 코드는 재사용하지 않는다. 다음 참가자는 다음 코드(예비 포함)를 받는다. 결과 표에 그룹별 배정·완료·이탈을 모두 적는다 |
| 오염 방지 | 모집 공고·동의서·안내에 가격을 적지 않는다. 참가자끼리 가격을 비교하지 않도록 개별 일정으로 진행한다. 인터뷰가 끝날 때까지 다른 가격을 언급하지 않는다 |
| 진행자 편향 | Paywall 단계에서는 참가자가 혼자 화면을 조작하고 진행자는 화면을 보지 않는다. 인터뷰 질문은 그룹과 관계없이 같다 |

## 3. 세션 프로토콜 (1회, 60~75분)

| 단계 | 시간 | 내용 | 이벤트 |
|---|---|---|---|
| 0 | 5분 | 연구 안내·동의(연구 동의 + 사진 AI 전송 동의). **"실제 결제는 일어나지 않는다"** 고지 | — |
| 1 | 3분 | 진행자가 참가 코드 입력 → 그룹 배정 | `experiment_assigned` |
| 2 | 15~20분 | 내 옷 5~8벌 등록(기존 기능). 사전에 등록해 와도 된다 | (제품 기능, 이 실험 이벤트 아님) |
| 3 | 10분 | 추천 보기, Missing Item → 상품 → 공식몰 이동(커머스 PoC, `BM_VALIDATION_PLAN.md` G2) | 커머스 이벤트(별도) |
| 4 | 10분 | **PLUS 체험**: 사려는 옷 사진 1장 → 활용도 분석 결과 확인. 원하면 1장 더 | `plus_feature_viewed` |
| 5 | 2~5분 | **연구용 Paywall**: 배정 가격 1개 → "고려하겠어요" 또는 "지금은 안 할래요" | `paywall_viewed`, `subscription_interest_selected` 또는 `subscription_declined` |
| 6 | 5분 | 설문(유용성 5점, 구매 판단 변화, 거절 이유) | — |
| 7 | 15분 | 인터뷰(가격 인식, 기능 가치, 실제 결제 의사, 원하는 기능) → 진행자가 완료 기록 | `interview_completed` |

- 참가자가 원하면 어느 단계에서든 중단할 수 있다. 중단은 이탈로 기록하고 이유를 관찰 기록지에 적는다.
- 4단계 체험 → 5단계 Paywall 순서는 모든 그룹이 같다. 체험 없이 가격만 보는 조건은 이번 실험에 없다.

## 5. 이벤트 스키마

### 5.1 공통 필드

| 필드 | 타입 | 필수 | 설명 |
|---|---|---|---|
| `event_id` | UUID | ✓ | 발생할 때 기기에서 만든다. 재전송해도 같은 값 → 중복 저장 방지 |
| `experiment_id` | text | ✓ | `r1-plus-price-v1` |
| `event_name` | enum | ✓ | 5.2의 6개(커머스 이벤트는 같은 저장소의 별도 이름, 5.4) |
| `participant_code` | text | ✓ | `^R1-[PT][0-9]{2}$`. **익명 참가자 ID** |
| `experiment_group` | enum | ✓ | `A` · `B` · `C` |
| `displayed_price_krw` | int | ✓ | 2900 · 4900 · 6900. 그룹과 일치해야 함(불일치 시 거부) |
| `occurred_at` | timestamptz | ✓ | 기기 시각(ISO 8601, 시간대 포함) |
| `received_at` | timestamptz | 서버가 채움 | 저장 시각(DB 방식만) |
| `feature_version` | text | ✓ | 예 `plus-wardrobe-fit@0.1.0`. 실험 중 수정하면 올린다 |
| `app_version` | text | ✓ | 앱 버전·빌드 번호 |
| `test_env` | enum | ✓ | `research`(본 실험) · `rehearsal` · `qa` · `dev`. 분석은 `research`만 |
| `platform` | enum | ✓ | `ios` · `android` · `web` |
| `session_id` | UUID | ✓ | 연구 참가 화면 진입마다 새로 만듦 |
| `properties` | JSON | — | 이벤트별 추가 값(5.2). 개인정보·자유 입력 금지 |

저장하지 않는 것: 이름, 이메일, 전화번호, 사진, 위치, 기기 고유 ID, 자유 입력 텍스트(거절 이유는 고정 선택지만).

### 5.2 필수 이벤트 6개

| 이벤트 | 언제 | 횟수 | `properties` |
|---|---|---|---|
| `experiment_assigned` | 참가 코드 입력 후 배정이 확정됐을 때 | 참가자당 **1회** | `consent_version`, `assignment_table_hash` |
| `plus_feature_viewed` | 활용도 결과 화면이 처음 표시될 때 | 참가자당 **1회**(다시 열어도 추가 기록 없음) | `matching_items`, `new_outfits`, `has_similar_item`(수치만) |
| `paywall_viewed` | 연구용 Paywall이 처음 표시될 때 | 참가자당 **1회** | — |
| `subscription_interest_selected` | "고려하겠어요"를 눌렀을 때 | 참가자당 **최대 1회**, 거절과 **둘 중 하나만** | `elapsed_ms`(Paywall 표시부터, 기기 단조 시계) |
| `subscription_declined` | "지금은 안 할래요"를 눌렀을 때 | 위와 같음 | `elapsed_ms`, `reason`(`price`·`not_needed`·`trust`·`other`·`skipped`) |
| `interview_completed` | 진행자가 인터뷰 완료를 기록할 때 | 참가자당 **1회** | `interviewer_role`(`PO`·`E1`·`E2`) |

- 실제 구독·결제 이벤트(`subscription_started`, `subscription_cancelled`, `paywall_view` 등 PRD 24.3의 Phase 5 이벤트)와 **이름·저장소를 공유하지 않는다.** 이 실험 이벤트는 매출·전환 집계에 들어가지 않는다.
- `subscription_interest_selected`는 "구독"이 아니다. 보고서에서는 **"구독 고려"** 로 부른다.

### 5.3 저장소 (결정 D1)

| 방식 | 내용 | 승인 |
|---|---|---|
| **A. 운영 DB `research_events`(권장)** | 삽입 전용(정식 로그인 사용자 본인만), 조회·수정·삭제는 관리자만. `event_id` 기본 키. 한 번만 기록하는 이벤트는 `(participant_code, experiment_id, event_name)` 고유. 고려·거절은 `(participant_code, experiment_id)`에서 하나만. 첫 배정 행으로 코드 ↔ 계정·그룹을 고정하고, 다른 계정·다른 그룹 행은 거부. `user_id`는 계정 삭제 연쇄(`on delete cascade`)용으로만 저장하고 **내보내기에서 뺀다** | **운영 DB 변경 승인(AP-1).** QA 프로젝트에서 먼저 검증 |
| B. 기기 기록 + 내보내기 | 앱 저장소에 이벤트를 쌓고, 세션 끝에 진행자가 내보내기 파일(JSON)을 받는다. 같은 규칙(고유·둘 중 하나)을 앱이 검사 | 불필요. 대신 기기 분실·앱 삭제 시 유실, 세션 밖 행동 측정 불가 |

두 방식 모두 같은 이벤트 형식을 쓰므로 분석 스크립트는 하나다.

### 5.4 같은 저장소의 커머스 이벤트(G2, 참고)

`product_impression`, `product_clicked`, `official_store_opened` — 같은 공통 필드(가격 필드는 상품 가격이 아니라 실험 배정 가격이므로 그대로 둠) + `properties.product_id`, `brand_id`, `utm_content`. 실제 구매·매출은 이벤트로 만들지 않는다(브랜드 보고만, `BM_VALIDATION_PLAN.md` 2장).

## 6. 중복 집계·재배정 방지

| 위험 | 방지 |
|---|---|
| 네트워크 재시도로 같은 이벤트가 두 번 저장 | `event_id` 고유. 서버는 같은 ID를 무시(1행 유지). 기기 대기열은 저장 확인 후에만 삭제 |
| 화면을 다시 열어 Paywall 노출이 여러 번 집계 | 한 번만 기록하는 이벤트는 고유 제약 + 앱의 "보냄" 표시 |
| 고려와 거절이 둘 다 기록 | 선택 후 버튼 비활성화 + 저장소에서 둘 중 하나만 허용 |
| 재설치 후 다른 그룹 | 그룹은 코드 → 고정 표로만 결정. 무작위 함수를 앱 실행 중에 쓰지 않음 |
| 다른 사람이 같은 코드 사용 | 첫 배정 계정 외에는 거부(방식 A). 방식 B는 진행자가 코드 사용 목록을 관리 |
| 그룹과 가격 불일치 | 저장 시 `group ↔ price` 대조, 불일치 거부 |
| 리허설·QA 데이터 섞임 | `test_env`·`R1-T` 코드로 분석에서 제외 |
| 실험 중 문구·기능 변경 | `feature_version` 기록. 변경이 있으면 결과 표에 버전별로 나눠 적음. 가격·문구는 실험 중 바꾸지 않음 |

## 7. 분석과 내보내기

### 7.1 결과 표 (그룹별)

| 항목 | 정의 |
|---|---|
| 배정 인원 | `experiment_assigned` 수 |
| 기능 체험 인원 | `plus_feature_viewed` 수 |
| Paywall 노출 인원 | `paywall_viewed` 수 |
| 구독 고려 인원 / 고려율 | `subscription_interest_selected` 수 / 노출 인원 |
| 거절 인원 / 거절률 | `subscription_declined` 수 / 노출 인원 |
| 선택 없음 | 노출 후 고려·거절 없이 종료 |
| 선택 소요시간 | `elapsed_ms`의 중앙값과 최소~최대(6명이라 평균 대신 중앙값) |
| 완료 / 이탈 | `interview_completed` 수 / 배정 후 미완료 수 + 이탈 단계(배정 후·체험 후·Paywall 후·인터뷰 전) |
| 거절 이유 분포 | `reason` 수 |

- 비율은 **"6명 중 3명"처럼 분모와 함께** 적는다. 유의성 검정 결과로 결론을 내리지 않는다(참고로 정확 검정 p값을 붙일 수는 있으나 판단 근거로 쓰지 않음).
- 인터뷰 응답과 연결해 "왜 고려/거절했는지"를 가격별로 정리한다.

### 7.2 내보내기 파일
