**핵심 판단**
1. 1라운드의 일은 **새 기능을 만드는 것이 아니라, 이미 있는 기능을 실제 사람·실제 기기·실제 데이터로 재는 것**이다. 새로 만드는 코드는 측정에 꼭 필요한 최소한(코디 저장, 측정 기록)과 Claude B가 요청한 출시 전 수정(H-1·H-4)으로 한정한다.
2. 목표 2의 "기존 추천엔진 비교"는 **기존 엔진의 기준선 측정**으로 해석한다. 새 Match Score 엔진 구현(Phase 1B-2·1B-3)과 앱 적용은 2라운드로 넘긴다. 결과가 좋든 나쁘든 "전문가 기준으로 본 현재 엔진의 수준"이 2라운드 엔진 개발의 근거가 된다.
3. 목표 1·3은 **실기기에 앱을 설치할 수 있어야** 시작할 수 있다. 이 경로는 Claude B 트랙과 PO 승인(백엔드 배포, 스토어 계정, Gemini 유료)에 달려 있다. 이것이 전체 일정의 최대 위험이다.

### 1.3 목표별 추가 작업

#### 목표 1 — 옷 등록→분석→추천→저장 성공률 90%

**성공 정의(제안, PO 확정 필요 — 결정 D1)**

| 단계 | 성공 | 실패로 세는 것 |
|---|---|---|
| ① 등록 | 사진 선택 후 분석 요청이 서버에 도착 | 앱 오류, 사진 준비 실패, 413 |
| ② 분석 | 30초 안에 속성 결과 표시(사용자 수정은 성공에 포함) | 429·5xx·타임아웃, 카테고리 오분류로 사용자가 등록을 포기 |
| ③ 옷장 저장 | 옷장에 **알아볼 수 있는 이미지**로 저장(SlimSAM·BRIA 결과. 원본 대체 저장은 별도 집계) | 저장 실패, 조각 이미지(KI-1 유형) |
| ④ 추천 | Styling 또는 Looks에서 저장한 옷이 들어간 코디가 1개 이상 표시 | 빈 화면, 오류 |
| ⑤ 코디 저장 | 추천 코디를 저장하고 다시 열었을 때 보임 | 기능 없음(현재) |

- **분모는 "시도"**(사진 1장의 등록 시도)이고, 단계별 성공률과 ①→⑤ 전체 성공률을 함께 보고한다. 참가자 1명이 여러 벌을 올리므로 참가자 단위 성공률도 따로 적는다.
- 두 가지로 잰다:
  - **기술 성공률(자동):** QA 프로젝트에서 실제 옷 사진 50장 이상(상의·하의·원피스·아우터·신발, 흰 옷·패턴·착용샷 포함)을 앱과 같은 순서로 처리. 기존 E2E(`backend/test/e2e`)를 사진 묶음 반복으로 확장
  - **사용자 성공률(관찰):** 목표 3 세션에서 진행자가 단계별 성공·실패와 원인을 관찰 기록지에 적는다. 자동 이벤트가 없어도 측정할 수 있다
- 90%는 **표본이 작으면 판정이 흔들린다**(시도 100회에서 90%의 95% 신뢰구간은 대략 83~95%). 결과 보고에 분모와 구간을 같이 적는다.

| 순서 | 먼저 검증할 것 | 이유 | 그 결과로 결정하는 것 |
