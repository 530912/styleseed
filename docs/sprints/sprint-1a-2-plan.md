## 5. 작업별 정의

### A. 익명 사용자 쓰기 차단 restrictive 정책

| 항목 | 내용 |
|---|---|
| 목적 | 익명 로그인을 켜도 익명 사용자가 옷장·사진을 저장하거나 읽지 못하게 한다. 현재 정책은 `authenticated` 역할 전체를 허용해 익명 사용자도 포함된다(AUDIT S-6) |
| 구현 | 새 마이그레이션 `supabase/migrations/<ts>_block_anonymous_writes.sql`: `public.clothes`와 `storage.objects`(`clothing-images`)에 **restrictive** 정책 추가 — `(select (auth.jwt()->>'is_anonymous')::boolean) is not true`. 기존 정책은 수정하지 않는다(추가만, 되돌리기는 정책 삭제 1줄) |
| 적용 순서 | ① QA 프로젝트에 적용 → E2E로 검증 ② **PO 승인 후** 운영에 적용 ③ MCP 읽기 전용 조회로 운영 정책 확인 |
| AC | ① 익명 세션으로 `clothes` 조회·추가·수정·삭제 0건 또는 거절 ② 익명 세션으로 `clothing-images` 업로드·조회 거절 ③ 정식 사용자의 기존 동작(저장·조회·삭제)은 그대로 ④ 운영 정책이 마이그레이션 파일과 일치 |
| 테스트 | QA E2E에 익명 사용자 시나리오 추가. 운영은 정책 메타데이터 읽기 확인 |
| 완료 기준 | AC ①~④. 운영 적용 전후 정식 사용자 회귀(E2E-05·06·07) 통과 |

### B. 익명 세션 도입 + 백엔드 등급 정리

| 항목 | 내용 |
|---|---|
| 목적 | 로그인 전 분석을 "토큰 없는 요청"이 아니라 Supabase 익명 세션으로 처리한다. PRD SEC-01과 응답 코드를 맞춘다(KI-2) |
| 앱 | ① 세션이 없으면 앱 시작 또는 첫 분석 직전에 `signInAnonymously()`(`src/lib/supabase.ts`·`_layout.tsx` 또는 `api.ts`) ② 저장 시 익명 상태면 기존처럼 가입·로그인 화면으로 이동 ③ **회원가입:** 익명 사용자를 `updateUser({ email, password })`로 정식 계정으로 전환(같은 사용자 ID 유지, 운영은 이메일 인증이 꺼져 있어 즉시 전환될 것으로 예상). **전환 동작은 Supabase 이메일 변경 설정에 따라 다를 수 있어 QA에서 먼저 확인**하고, 안 되면 기존처럼 `signUp`으로 새 계정을 만든다(같은 ID 유지는 포기, 보류 중인 옷은 기존 방식대로 저장) ④ **기존 계정 로그인:** 기존처럼 `signInWithPassword`로 세션 교체(익명 세션은 버려짐) ⑤ 로그아웃 후 다시 익명 세션 |
| 백엔드 | ① 토큰 없는 `/analyze-clothing` → **401**(PRD SEC-01 ①) ② 익명 토큰은 분석만 허용, 이미지 처리는 **403 `ANONYMOUS_NOT_ALLOWED`**(PRD SEC-01 ②) ③ 익명 분석 한도: 익명 사용자 ID 기준 시간당 10회 + IP 기준 상한(익명 세션을 새로 만들어 우회하는 것 방지) ④ 정식 사용자는 지금처럼 무제한(영구 한도는 1A-08) |
| 전환기 호환 | 앱 업데이트 전 버전(토큰 없이 분석)이 있을 수 있으므로, 토큰 없는 분석을 401로 바꾸는 것은 **앱 배포와 같은 시점**에 환경변수(`ALLOW_TOKENLESS_GUEST`, 기본 off)로 전환할 수 있게 한다. 현재는 배포 전이라 실제 영향은 없음 |
| 운영 변경 | **PO 승인 후** 운영 Auth에서 "Allow anonymous sign-ins" 켜기(작업 A 적용 뒤에만) |
| AC | ① 앱을 처음 열면 익명 세션이 생기고 로그인 없이 분석된다 ② 익명으로 분석 → 회원가입하면 **같은 사용자 ID**로 옷이 저장된다 ③ 익명으로 분석 → 기존 계정 로그인 시 그 계정에 옷이 저장된다 ④ 토큰 없는 분석 401, 익명 토큰 이미지 처리 403, 정식 토큰 정상 ⑤ 익명 한도 초과 시 안내 문구 ⑥ 익명 세션을 계속 새로 만들어도 IP 상한에서 막힌다 |
| 테스트 | 백엔드 단위 테스트(등급·코드), 앱 순수 함수 테스트, QA E2E(익명 → 분석 → 가입 전환 → 저장, 익명 → 기존 계정 로그인 → 저장) |
| 완료 기준 | AC ①~⑥. AC-G3 ①~③ 충족. KI-2 닫힘 |

### C. SSRF 차단

| 항목 | 내용 |
|---|---|
| 목적 | 서버가 요청 본문의 임의 URL(`imageUrl`)을 가져오지 않게 한다(AUDIT S-2, SEC-03) |
| 구현 | ① 앱은 서명 URL 대신 **Storage 경로**(`{userId}/originals/...`)를 보낸다(`src/lib/clothes.ts`) ② 서버는 경로의 첫 폴더가 토큰의 사용자 ID와 같은지 확인한 뒤, **그 사용자의 토큰으로** Supabase Storage 서명 URL을 직접 만든다(관리자 키 불필요, RLS가 한 번 더 확인) ③ 4개 이미지 처리 경로 모두 적용, `imageUrl` 입력은 받지 않음 |
| AC | ① 외부 URL·내부 IP 입력은 400 ② 다른 사용자 폴더 경로는 403 ③ 정상 저장 흐름(배경 제거)은 그대로 |
| 테스트 | 백엔드 단위 테스트 + QA E2E(B 사용자가 A 경로로 처리 요청 → 403) |
| 완료 기준 | AC ①~③, 서버 코드에 요청 본문의 URL을 직접 `fetch`하는 곳 0건 |

### D. 배경 제거 품질 게이트 + 품질 기록 (KI-1)

| 항목 | 내용 |
|---|---|
| 목적 | **API 성공(200)과 실제 분리 품질을 구분한다.** 잘못 잘린 결과가 옷장에 저장되지 않게 한다 |
| 구현 | ① 서버: SlimSAM 결과를 반환하기 전에 품질 판정 — 마스크 면적이 Gemini box 대비 기준(초안 25%) 미만이거나 투명 비율이 5% 미만·95% 초과면 **422 `LOW_QUALITY_CUTOUT`** ② 마스크 선택 개선: 여러 마스크 중 box를 가장 잘 덮는 것을 고르거나, box 단독 프롬프트로 다시 시도(흰 셔츠 진단에서 box 단독 시 57% 정상) ③ 앱: 422를 받으면 기존 BRIA 대체 경로로 넘어간다(현재 실패 시와 동일 처리) ④ 품질 기록: 처리 경로(sam/bria/original)와 지표(box 대비 면적, 투명 비율)를 서버 로그에 남긴다(PRD NFR-08 기준선) |
| AC | ① E2E-09(흰 셔츠)가 일반 테스트로 통과: 셔츠가 분리되거나, 저품질로 판정되어 BRIA로 대체 ② 정상 이미지 3종(스니커즈·로퍼·데님)은 SlimSAM으로 그대로 성공 ③ 저품질 결과가 `cutout_image_path`로 저장되지 않는다 ④ 경로·지표 로그 기록 |
| 테스트 | QA E2E 확장(이미지 4종 이상), 품질 판정 함수 단위 테스트 |
| 완료 기준 | AC ①~④. KI-1 닫힘. 품질 평가 세트를 정기 측정할 수 있는 명령 1개 |
